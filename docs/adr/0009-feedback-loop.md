# ADR-0009：反馈闭环 —— 把线上对话变成可复用的评测资产

- 状态：已采纳
- 日期：2026-10-26
- 关联：ADR-0006（智能体循环）、ADR-0007（MCP 与 Skills）、ADR-0008（路由分诊）

## 背景

到 ADR-0008 为止，能力这条线是通的：智能体能规划、能调工具、能走 MCP、能命中技能、
能分诊到不同坐席。但**没有证据链**。

具体表现为三个问题：

1. **改一版提示词，凭什么说变好了？**
   手里只有 `eval/run_eval.py` 里 10 条手写用例。它们覆盖的是"我们以为重要的场景"，
   不是"用户实际遇到的场景"。而且这 10 条一旦写死，模型和提示词都会围着它过拟合——
   分数涨了，线上未必好。

2. **用户不满意的对话每天在流失。**
   用户骂一句就走，我们什么也没留下。下一版还会犯同一个错，因为没人知道犯过。

3. **"答得对"和"做对事"混在一起看。**
   客服场景里最贵的错误不是措辞不好，是「该查的没查就编了一个数」「该建工单却只道了个歉」。
   这类错误只能靠**用户当场指出**，事后从日志里猜是猜不出来的。

## 决策

### 1. 网关是唯一写入点，事件溯源、只追加

数据面只有一个写者：Node 网关。Python 智能层不写文件。
好处是两个后端（`AGENT_BACKEND=ts|py`）产出的数据形状完全一致，可以混在一起分析；
代价是 Python 侧的 `agent/skill/route` 必须通过 `done` 帧回传，由网关落盘。

文件是 append-only 的 JSONL，两种行：

```jsonc
// A. 一轮对话的事实（每个 traceId 写一次）
{"kind":"turn","traceId":"trace_...","sessionId":"sess_...","ts":1792994130501,
 "channel":"web","question":"三人位多少钱","answer":"三人位 2999 元……",
 "cardType":"kb_ref","planner":"router","agent":"presale","route":"rule",
 "toolCalls":["kb_search"],"degraded":false,"firstTokenMs":412,"totalMs":1650}

// B. 一次用户评价（同一 traceId 可写多次）
{"kind":"feedback","id":"fb_...","traceId":"trace_...","ts":1792994200112,
 "rating":"down","reasons":["missing_tool"],"comment":"没让我确认",
 "correctedAnswer":"沙发异味属质量问题，7 天内可退换，需先建售后工单","channel":"web"}
```

读取时按 `traceId` 折叠：turn 打底，feedback 后写的覆盖先写的，同时记数。

**为什么不就地改一行：**

| | 追加 | 改写 |
|---|---|---|
| 并发 | O_APPEND 原子，不用锁 | 读全量→改→重写，两个请求撞上就丢 |
| 回放 | 用户先👎后改👍，两条都在 | 只能看到最后一次，改主意这个信号丢了 |
| 故障 | 最坏丢最后一行 | 最坏毁整个文件 |

代价是读取要折叠。MVP 全量读 + mtime 缓存；文件到十万行换 SQLite 或 ClickHouse，
**换的时候折叠规则要一起搬**，否则历史评价会对不上。

### 2. 脱敏放在写入，不放在导出

反馈数据迟早要离开这台机器——做标注、跑评测、给外包看。一旦联系方式进了 JSONL，
后面每一步都得记得再脱一次，而漏点是必然的。所以在唯一入口做一次，下游全是干净数据。

只脱「人」的信息，不脱「业务」的信息：

| 字段 | 处理 | 理由 |
|---|---|---|
| 手机号 | `138****5678` | 够人工核对，不够直接拨打 |
| 身份证 | `110101********8888` | 保留地区 + 校验位 |
| 银行卡 | `6222 **** **** 1234` | 同上 |
| 邮箱 | `***@example.com` | 保留域名（域名的商业价值高于账号） |
| **订单号 / 运单号** | **原样保留** | 回放查证的主键，抹掉样本就废了 |

规则顺序是长的先跑（身份证 → 银行卡 → 手机 → 邮箱），否则 18 位身份证会被 11 位手机号规则切碎。

### 3. 反馈必须挂在真实存在的 traceId 上，差评必须选原因

- 没有 traceId 校验，前端一个 typo 就能在生产库里堆满孤儿评价，而且这些脏数据会**静默**污染好评率。
  校验后返回 404，比事后查账便宜得多。
- 差评原因固定 6 项：`wrong_fact` / `missing_tool` / `wrong_action` / `too_vague` / `format` / `slow`。
  **刻意不放"其他"** —— 开放选项会变成垃圾桶，90% 的差评都选它，聚合就没意义了。
  说不清原因的，用「正确答案应该是……」来表达。

### 4. 样本分四级，权重不同

| 反馈 | 有修正答案 | label | weight | 用途 |
|---|---|---|---|---|
| 👎 | 有 | `human_corrected` | 1.0 | **金样本**：既是负例又是正例，直接进回归集 |
| 👎 | 无 | `human_rejected` | 1.0 | 只知道"错了"，只能验工具/动作，验不了文案 |
| 👍 | — | `bot_accepted` | 0.5 | 自举样本 |
| 无反馈 | — | `unlabeled` | 0 | 只做分布统计，**不进评测** |

三条规矩值得单独说：

- **👍 只有 0.5 权重。** 用户认可只证明"没出错"，不证明"最优"；用户没义务替你挑毛病。
- **unlabeled 一律不打分。** 把模型自己答的当期望答案再考模型，分数必然接近满分。
  这是自欺欺人，比没有指标更危险。
- **差评不推导期望工具。** 差评恰恰说明这次调用有问题，拿它当答案就是反着学。
  只有 👍 且确实调了工具，才认为这次调用是对的。

### 5. 自动事实抽取：宁缺毋假阳

从参考答案里只抽三类实体：

```
(?:CS|SF|JD)\d{4,}                       单号
\d{4}-\d{2}-\d{2}                        日期
\d+(?:\.\d+)?\s*(?:个工作日|元|折|天|小时|分钟|个|件|台)   数量 + 单位
```

不猜「已签收」「运输中」这类业务状态词。**猜错一次，整套指标就没人信了。**
代价是召回低——事实命中只是必要条件，不是充分条件。这一点在报表里必须写明，
否则会被当成"通过率 = 正确率"来用。

### 6. 两套分数分开报，不混

```
内置用例（10 条手写）  = 我们认为重要的场景，稳定但会过时
反馈数据集（用户产生） = 用户实际遇到的场景，覆盖真实分布但噪声大
```

两者都要有：只有前者会自我感觉良好，只有后者会越跑越偏。

`run_eval.py --dataset x.jsonl` 只读反馈数据集，评分维度按「可判分字段」自动组合：

- 卡片/工具属于「做对事」，权重高于「说对话」（工具+事实 = 0.6/0.4，与内置用例口径一致）；
- 一个可判分字段都没有的样本，标记「不可判分」并计入 `--strict` 的失败项，
  **绝不默认给 1 分**。默认给满分是评分系统最常见的自欺。

## 落地形态

```
浏览器 👍/👎
   │  POST /api/feedback {traceId, rating, reasons[], correctedAnswer?}
   ▼
网关 data/routes.ts ── 校验 ──▶ TraceStore.appendFeedback
                                   │  var/data/feedback.jsonl（追加 + 脱敏）
                                   ▼
                             折叠读（turn + 最新 feedback）
                                │                    │
                     GET /api/stats/feedback   GET /api/dataset/export
                       （好评率/原因分布/按坐席）        （jsonl 附件）
                                                        │
                                          eval/run_eval.py --dataset
```

验证过的接口行为：

| 场景 | 结果 |
|---|---|
| 👍 直接提交 | 200，落一条 `rating=up` |
| 👎 未选原因 | 400 `reason_required` |
| 原因不在枚举内 | 400 `reason_invalid` |
| traceId 不存在 | 404 `trace_not_found` |
| 同一轮先👎后改👍 | 折叠后 `rating=up`，`feedbackCount=2` |

## 已知限制（必须写清楚，否则会被当成"已经做完了"）

1. **单机单文件。** 多实例部署前必须换 SQLite/ClickHouse，或者改成对象存储 + 队列。
   `appendFileSync` 在 NFS 上不保证原子。
2. **没有语义判分。** 没有 judge 模型，"说得对不对"仍然要靠人看。
   现在能自动判的只有工具选择、卡片、数字/单号类事实。
3. **样本有选择偏差。** 点反馈的是少数人，且以不满者为主。
   `satisfaction` 不能当 NPS 用，只能当趋势看。
4. **缺数据生命周期。** 没有保留期、没有按用户删除的接口。
   真要上生产，这是合规硬门槛（个保法/DSGVO），不是 nice-to-have。
5. **反馈是"事后"的。** 它改善的是下一版，救不了当下这一轮——
   即时兜底仍要靠转人工（ADR-0006 的护栏）。

## 后续

1. 标注队列：把 `human_rejected|needs_annotation` 的样本捞出来，做成一个可批量改写的内部页面；
2. judge 模型：接一个强模型做对比判分，只对金样本抽检，控制成本；
3. 灰度对照：同一批数据集跑 A/B 两版提示词，按坐席维度看谁退步了；
4. 把「差评原因 × 坐席」做成看板，直接回答"哪个坐席最需要重写提示词"。
