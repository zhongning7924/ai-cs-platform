# ADR-0005: 文档源连接器（本地文件 / 飞书 / 钉钉）

日期：2026-10-25 ｜ 状态：已采纳（飞书已实现，钉钉有明确路线）

## 背景

个人与企业的知识库不止存在于本地文件：企业现状往往是「钉钉 + 飞书 + 语雀 + Confluence」混合。
存储层（ADR-004：Qdrant + 硅基流动）只关心"文本 + 向量"，文档从哪来是**源连接器层**的职责。

## 决策

采用 **SourceProvider 模式**：每种源实现为独立连接器，统一产出 `KbDocument { id, title, text, uri }`
后走同一条 ingest 管道（chunker → bge-m3 → Qdrant）。检索层对文档来源零感知。

| 源 | 状态 | 方式 |
|---|---|---|
| 本地文件（md/txt/pdf/docx） | ✅ 已实现 | kb-cli ingest；PDF=unpdf，docx=mammoth |
| 飞书知识库 | ✅ 已实现 | 开放平台 API：`raw_content`（近似 markdown）+ wiki 节点树遍历 |
| 钉钉文档 | 📋 路线已定 | 见下文 |
| URL / 站点抓取 | P2 | fetch + readability 正文抽取 |
| 语雀 / Notion | P3 | 同 SourceProvider 模式，各 ~150 行 |

## 关键设计

1. **docId 绑定源标识**：本地文件=路径 sha1；飞书=`feishu:{node_token}` sha1。重复同步幂等覆盖。
2. **引用回链**：飞书文档的 uri 是 `feishu.cn/wiki/{node_token}`，检索结果可点击跳回原文。
3. **命名空间隔离**：企业库建议 `--ns company`，与个人库（personal）物理隔离，检索互不串。
4. **权限最小化**：飞书只申请 readonly 两个 scope；应用可用范围决定能看见哪些空间。
5. **不支持即跳过**：旧版 doc / 表格 / 思维笔记等无文本 API 的类型跳过并计数，不阻塞整库同步。

## 钉钉路线（为什么不现在做）

钉钉开放平台对「文档正文」的 API 覆盖弱于飞书（新版文档 API 以列表/元数据为主，正文导出
能力受限，且企业版权限审批链长）。三条落地路线，按优先级：

1. **导出通道（最快，0 开发）**：钉钉文档批量导出为 docx/pdf → 放入 `~/kb-sources`
   （或服务器 watch 目录）→ 走现有 ingest。适合一次同步、低频更新。
2. **钉钉连接平台 / 自建应用**（P2）：走官方「文档」OpenAPI 列文档清单 + 钉盘下载，
   结合导出能力定时拉取。
3. **RPA 兜底**（P3，不推荐先做）：自动化操作页面导出，脆且违反平台精神。

结论：先上飞书连接器（API 完整），钉钉走导出通道应急，P2 再评估官方 API 成熟度。

## 后果

- 正面：企业文档接入从"不可能"变为"配两个 key 跑一条命令"；引用链可回溯原文。
- 代价：连接器各自维护鉴权与分页逻辑（每个 ~150 行，可控）。
- 风险：飞书 API 限流（当前量级远未触及）；文档删除不会自动从库中移除
  （需 `remove` 或后续做对账清理，已列入 P2 待办）。
