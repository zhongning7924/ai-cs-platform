# ADR-0010：私有化交付形态

- 状态：已采纳
- 日期：2026-10-26
- 关联：ADR-0003（分层）、ADR-0009（数据面）

## 背景

产品形态确定为**私有化交付**：一套代码交付给一家客户，跑在客户自己的机房或专有云里。

客户环境有两个硬约束：

1. **单商户单实例** —— 一台机器服务一家客户，不存在「A 商户看到 B 商户知识库」的场景。
2. **仅白名单出网** —— 能连指定域名，但不能自由访问公网。

这两个约束推翻了先前按 SaaS 预设的一批设计，也把另一些问题的优先级彻底重排。

## 决策

### 1. 不做多租户

不加 `tenant_id`、不做按租户隔离的集合与数据分区、不做计费与配额。

隔离由**物理边界**保证：一台机器一家客户。引入租户维度只会让交付变重（多一层配置、多一类越权 bug、多一份排查成本），而收益为零。

`KB_NAMESPACE` 保留，但职责改为「区分正式库与测试库」，不承担隔离。

### 2. 模型端点拆成三套独立配置

原先 LLM / embedding / rerank 共用一个 `SILICONFLOW_BASE_URL`。私有化现场这三者几乎从不同源：embedding 跑在内网 TEI，rerank 挂在集团 AI 平台，LLM 走统一网关。

拆分为：

| 配置 | 回退顺序 |
|---|---|
| `LLM_BASE_URL` / `LLM_API_KEY` | → `SILICONFLOW_*` |
| `EMBEDDING_BASE_URL` / `EMBEDDING_API_KEY` | → `SILICONFLOW_*` |
| `RERANK_BASE_URL` / `RERANK_API_KEY` | → Embedding → `SILICONFLOW_*` |

回退设计保证云上现有部署零改动；rerank 继承 embedding 是因为同一台 TEI 常常同时提供两者。

`kb_ready` 从「三个 key 齐全」放宽为「Qdrant URL + embedding key」。自建 Qdrant 通常不开鉴权，硬要求 `QDRANT_API_KEY` 会让本地容器部署在启动时就失败——这是最容易在交付现场踩的坑。

### 3. 管理面用共享 token，不是账号体系

`/api/traces`、`/api/stats/feedback`、`/api/dataset/export` 导的是客户隐私（对话原文、订单号）。不能匿名 GET 就能拉走。

但也不需要用户/角色/会话：单商户、单运维，一个 `ADMIN_TOKEN` 足够。

**未配置时不直接放开**，而是降级为「只允许本机访问」。默认不设防的产品，交付到客户内网会被安全审计打回；而直接拒绝又会让本地开发卡住。只允许 loopback 是这两者之间唯一合理的位置。

### 4. 挂件防护用来源白名单，不是登录

商户官网是公网。挂件一嵌，`POST /api/chat` 就暴露了。两个真实风险：

- 同行直接 curl 这个端点，把商品/价格/库存知识库爬空
- 把挂件嵌到自己站点上白用

这跟「用户是谁」无关，只跟「请求来自哪个页面」有关，所以校验 `Origin` / `Referer` 就够。浏览器对 POST 一定带 `Origin`，正常挂件不受影响；脚本调接口会被挡。

留空 = 不校验，仅供本地联调。上线必须填，且要包含网关自身地址（内置演示页的 Origin 就是它）。

### 5. 限流的目的不是省钱

私有化下 LLM 的 key 是客户自己的，刷爆了不心疼。但单实例被一个脚本打满，等于**全站客服同时挂掉**——那是交付事故，不是账单问题。

所以限流按 IP＋分钟做进程内滑动窗口，`RATE_LIMIT_PER_MINUTE=0` 可关（压测需要）。

### 6. 交付物是 docker compose，不是 K8s

客户运维只需要会 `docker compose up -d`。三个容器：`qdrant`（内部，不映射端口）、`agent`（内部）、`gateway`（唯一对外）。

镜像用「有网机器构建 → `docker save` → 内网 `docker load`」的方式搬运，现场 `--no-build`。

## 后果

### 变简单的

- 不需要租户路由、行级权限、配额系统
- 不需要 Redis / 消息队列 / K8s
- 会话可以继续放在进程内存里（单实例前提）

### 变复杂 / 需要记住的

- **单实例是硬约束**。加实例之前必须替换三处进程内状态：会话 Map、限流计数、BM25 词表与 `InMemoryMemory`。不换就扩容，表现为「同一用户换台机器就失忆」——是正确性问题，不是性能问题。
- 数据面（`var/data/*.jsonl`）也只在单机安全：NFS 上 `appendFileSync` 不保证原子。
- 管理面只有一个共享 token，不区分操作人。多人运维时审计追不到具体是谁导出的数据。

## 未解决（按阻断程度）

1. **业务工具是 mock**：`query_order` / `create_ticket` 用内存假数据，接不了真单。
2. **没有转人工**：兜不住的问题没有出口，这是客服业务的底线。
3. **无数据保留期与删除接口**：合规硬门槛，私有化客户同样会问。
4. **可观测性只有 console.log**：不在现场时，日志和指标是唯一抓手。
